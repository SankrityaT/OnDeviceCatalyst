# ODC-0011 / ODC-0012 / ODC-0015 review pass two (adversarial)

## Verdict

**ODC-0011: REJECT, return to REVISION.**
**ODC-0012: REJECT, return to REVISION.**
**ODC-0015: REJECT, return to REVISION.**
**Ordering claim ("ODC-0012, then ODC-0015; ODC-0011 unordered"): CONFIRMED, independently re-derived from source, not just taken on the specs' word.**

This continues the program's unbroken pattern (ODC-0002, ODC-0003, ODC-0004,
ODC-0005, ODC-0100, all REJECT at pass two): the discovery work in all three
specs is unusually strong and every root-cause claim I attempted to falsify
against the actual source held up almost exactly as stated, to the line
number, in most cases. But each spec carries at least one finding I classify
BLOCKING under this program's own standard (any verifiable factual error in a
load-bearing claim, or any code-shape gap that would ship a residual instance
of the defect under repair, is grounds for REJECT, not "accept with
revisions" - see ODC-0004 finding 1, ODC-0004 finding 2, ODC-0005 finding 1,
ODC-0005 finding 2). Given this batch produces the project's first runtime
source changes, I held the bar at the same place, not lower.

The three BLOCKING findings are narrow and independently fixable without
touching the core repair design of any of the three specs:

- **ODC-0011** (finding 1): the metadata-relocation design, if implemented
  exactly as the "In-scope repair" section is worded, leaves
  `ResponseMetadata.completionReason` hardcoded to `.natural` forever, even
  after `StreamChunk`'s own `reason:` is fixed. This reproduces the ticket's
  own defect one level deeper, inside the "full metadata" the fix exists to
  deliver, and no test in the flip table would catch it.
- **ODC-0012** (finding 2): the review record's ordering-hazard argument
  overstates its own case. It claims that landing ODC-0015 first would make
  *both* the fallback path and the non-recoverable path hang. I independently
  traced ODC-0015's own design and found the non-recoverable branch keeps an
  explicit safety-net `cleanup()` call that terminates the stream regardless
  of the gate's state. Only the recoverable/fallback branch would actually
  hang. The direction of the mandatory ordering is still correct; the stated
  reason for it is partly wrong, in a document whose only asserted defense
  for a hard ordering constraint is that reasoning.
- **ODC-0015** (finding 3): the concrete recoverable-error examples cited for
  the "warmup leaves a backend assigned" leak scenario - `.memoryInsufficient`
  and `.samplingFailed` - are not reachable from `warmup()` at all.
  `.memoryInsufficient` is thrown nowhere in the codebase. `.samplingFailed`
  is thrown only by `LlamaSamplerChain` init and `SamplingEngine.sampleToken`,
  never by `warmup()`. The scenario itself is real, but through a mechanism
  the spec never names: `LlamaCppBackend.warmup()` calls
  `LlamaBridge.processBatch`, which throws `.batchProcessingFailed` - also
  `isRecoverable == true`, and the only error `warmup()` can actually surface
  that is.

All three are one- or two-sentence-plus-one-test-assertion fixes. None of
them requires re-architecting the repair. Below is the full attack-by-attack
record, then the minimum change set per spec.

## Attack 2: ODC-0011's metadata-relocation risk - BLOCKING (finding 1)

`ResponseMetadata` (`Core Foundation/CompletionReason.swift:108-133`) declares
its **own** `completionReason: CompletionReason` field, entirely separate
from `ChunkMetadata.completionReason` (`StreamResponse.swift:60`, populated
from the `reason:` argument passed to `StreamChunk.completion(reason:,
metadata:)`, `StreamResponse.swift:28-34`). Today, `performGeneration`
constructs `ResponseMetadata(completionReason: .natural, ...)` at
`LlamaInstance.swift:375-382`, hardcoded, and separately passes `reason:
.natural` to `.completion(reason:, metadata:)` at `:384`. Both copies are
wrong today, for the same reason.

`StreamingResponse.addChunk` (`StreamResponse.swift:90-99`) sets
`completionReason = chunk.metadata?.completionReason` (the `ChunkMetadata`
copy) and, **separately**, `metadata = chunk.metadata?.responseMetadata` (the
full `ResponseMetadata`, including its own nested `completionReason`). Both
are public, `Codable`, and reachable by any external consumer of this
library - `Catalyst.swift:298` already reads `chunk.metadata?.responseMetadata`
into a local (`completionMetadata`, currently a genuinely unused variable,
confirmed by the v2.0.4 baseline's own warning inventory, but the field it
reads is public API regardless of whether this one in-repo caller uses it).

ODC-0011's "In-scope repair" step 3 reads:

> consume the returned reason, build `ResponseMetadata` exactly as today
> (unchanged fields and computation), and yield exactly one
> `StreamChunk.completion(reason:, metadata:)` using the *real* reason rather
> than a hardcoded `.natural`

Read literally, "build `ResponseMetadata` exactly as today (unchanged fields
and computation)" instructs keeping the `ResponseMetadata(completionReason:
.natural, ...)` construction **as-is**, and "using the real reason" is
grammatically attached only to the outer `.completion(reason:, metadata:)`
call. An implementer following this text produces a chunk where
`chunk.metadata?.completionReason` (outer) correctly reports the real reason
and `chunk.metadata?.responseMetadata?.completionReason` (nested, "the full
metadata") still unconditionally reports `.natural`. That is the exact defect
class this ticket exists to remove - "two places disagree about why
generation stopped" - reproduced one level deeper, inside the single
surviving chunk, in the field the spec's own prose calls "the full
`ResponseMetadata`."

This is not a hypothetical reading. I checked whether any test in the spec's
own flip table (`## Tests`) would catch it: `makeD2ChunkStream` in
`StreamContractCharacterizationTests.swift:27-34` constructs completions via
`.completion(reason: realReason)` with **no `metadata:` argument**, so
`metadata` is `nil` in every existing characterization case. No test anywhere
in the current suite, nor any test named in ODC-0011's flip table, reads
`.metadata?.responseMetadata?.completionReason`. The gap would ship silently.

**Fix**: state explicitly, in the repair steps, that `ResponseMetadata`'s own
`completionReason:` argument must also be constructed from the real,
returned reason, not `.natural` - i.e., "build `ResponseMetadata` with the
real reason and otherwise-unchanged fields and computation." Add one
assertion to the `userCancelled` regression test (already planned as new,
per the spec's own `## Regression risks`) or to a new case: after the fix, a
completion chunk's `metadata?.responseMetadata?.completionReason` equals
`metadata?.completionReason` for every one of the five reasons, not just for
`.natural`.

## Attack 3: the ordering hazard - CONFIRMED, but its stated scope is partly wrong (finding 2)

I independently re-derived the ordering claim rather than accepting the
specs' narrative, using `Tests/OnDeviceCatalystTests/Support/StreamRecorder.swift:28-50`,
which is the actual harness every `R2`/`R3` case in this suite uses to decide
"terminated." Its `record(_:timeout:)` drains via a bare `for await element in
stream { events.append(element) }` with **no early break on element
content** - termination is decided purely by the stream itself finishing (or
a watchdog `Task.sleep` cancelling the collector after the bound). This
matters: it means the *test harness itself* would actually hang for the
full liveness bound (20s in `InitializationFailureCharacterizationTests.swift:26`)
if a code path stopped delivering `AsyncStream` closure, which is exactly the
scenario the ordering hazard claims.

Tracing ODC-0015's own repair design (not a naive strawman) against a
still-unfixed `publishProgress` gate:

- **Non-recoverable branch** (step 2 of ODC-0015's repair): publish
  `.failed(...)` first, "then release resources (equivalent to today's
  `cleanup()`, including finishing `loadingContinuation` as a safety net)."
  This safety-net `cleanup()` call finishes `loadingContinuation`
  **unconditionally** - its `loadingContinuation?.finish()` at `:246-247` is
  not gated by `publishProgress`'s broken predicate at all. So this branch
  **would still terminate the stream** even with ODC-0012 unfixed. It would
  not hang.
- **Recoverable branch, fallback succeeds** (step 3): `attemptFallbackInitialization`
  assigns the new backend, then calls `publishProgress(.ready(...))` at
  `:224`, with **no cleanup call following it** ("the fallback's own
  resources must survive"). With the gate unfixed, this `.ready` value is
  delivered (the `yield` runs unconditionally) but the continuation is never
  finished. This **would** hang, exactly as claimed.
- **Recoverable branch, fallback fails** (step 3's catch): publishes
  `.failed(...)` at `:227`, again with no cleanup call specified to follow
  it in the ticket's own design (resource cleanup for the partial state is
  routed into the catch branch itself, per Q1, not paired with a
  continuation-finishing safety net). With the gate unfixed, this **would
  also** hang.

So the ordering hazard is real and independently confirmed for **the
recoverable/fallback branch, both of its own outcomes** - this is the
consequential, correct part of the claim, and it is why `ODC-0012` must land
first. But ODC-0012's `## Review record` states the hazard as: "fallback-path
**and non-recoverable-path** `publishProgress(...)` calls" would "hang rather
than silently drop." The non-recoverable path, under ODC-0015's own specified
design, does not hang - its safety-net `cleanup()` call is independent of the
gate. This is an overstatement in a load-bearing section: it is the sole
stated justification for a hard, non-negotiable landing-order constraint
between two of these three tickets, and part of its factual basis does not
hold up against the other spec's own text.

**Fix**: narrow the claim in ODC-0012's `## Review record` to the branch it
actually applies to (the recoverable/fallback branch, on either of its two
outcomes), and drop or correct "non-recoverable-path." The landing-order
requirement itself (`ODC-0012` before `ODC-0015`) is unaffected - it is still
necessary, just for a narrower reason than stated.

## Attack 4: ODC-0012's blast radius - clean

Every consumer of `LoadProgress` streams in `Sources/` was enumerated (four
sites, `Catalyst.swift:150,205,397,655`, confirmed exhaustive by direct
`grep`). All four decide their own loop exit locally, either via
`progress.isComplete` or an equivalent direct `case .ready`/`case .failed`

make work correctly, not a production consumer whose contract changes.
`MLXInstance.swift` already ships the corrected predicate today, which is
independent, already-compiling evidence the change is safe in this codebase.

I found no consumer, in `Sources/`, `Tests/`, or the two orphaned/uncompiled
files under `Tests/` (`EmbeddingTest.swift:30`, `BERTEmbeddingTest.swift:29`,
neither compiled into any target per the v2.0.4 baseline's own test
inventory), that relies on the loading stream never terminating.

## Attack 5: ODC-0015's `cleanup()` split - design is safe; illustrative citation is wrong (finding 3)

**Is the split itself safe?** Yes. `cleanup()`'s own body (`:237-248`) is
untouched by the repair; every operation inside it is nil-coalescing
(`backend?.shutdown()`, `loadingContinuation?.finish()`) and therefore
idempotent - calling it a second time as a "safety net" after an already-run
partial release is a harmless no-op, not a double-free. The new partial
release the recoverable branch needs (shut down and nil `backend` and
`samplingEngine`, but not `loadingContinuation`) is a genuinely new, small
helper distinct from `cleanup()`; nothing in the repair asks `cleanup()`
itself to be restructured, so `shutdown()` and `deinit`'s existing, unrelated
call sites are unaffected.

**Is the resource-leak scenario the spec cites real?** The general shape is
real - a recoverable `CatalystError` thrown by `warmup()` (`:118`, after
`self.backend`/`samplingEngine` are assigned at `:110`/`:113`) does leave a
live backend behind that `attemptFallbackInitialization` would otherwise
silently overwrite at `:214` without shutting it down first. I confirmed
this class of leak is real and is exactly what step 3 exists to close.

**But the two named examples cannot occur.** The spec says: "`isRecoverable`
is `true` for, among others, `.contextCreationFailed`, `.memoryInsufficient`,
and `.samplingFailed`... a recoverable error surfaced by warmup (plausible
for `.memoryInsufficient` or `.samplingFailed`...)". I traced every throw
site in the package:

- `CatalystError.memoryInsufficient` is **never thrown anywhere in
  `Sources/`** (`grep -rn 'CatalystError\.memoryInsufficient' Sources/`
  returns zero results). It is dead code today - declared, marked
  recoverable, given a `recoverySuggestion`, but unreachable.
- `.samplingFailed` is thrown only by `LlamaSamplerChain.swift:43,84,97,108`
  (sampler-chain construction) and `SamplingEngine.swift:333` (during
  token sampling in `generateTokens`, i.e. generation time, not
  initialization). `SamplingEngine`'s own `init(vocabularySize:)`
  (`SamplingEngine.swift:15`) is non-throwing - confirmed by the call site
  at `LlamaInstance.swift:113` having no `try` - so it cannot be the source
  either.
- `LlamaCppBackend.warmup()` (`Backend/LlamaCppBackend.swift:41-58`) can only
  throw three things: `.engineNotInitialized` (not recoverable),
  `.tokenizationFailed` (not recoverable), or whatever
  `LlamaBridge.processBatch` throws at `LlamaBridge.swift:317-331` -
  which is `.batchProcessingFailed`, and `.batchProcessingFailed` **is**
  `isRecoverable == true` (`CatalystError.swift:95-96`). This is the one and
  only mechanism by which the cited leak scenario can actually happen on the
  primary path today, and the spec never names it.

This does not change the repair's design - step 3 is correct however the
recoverable error arrives - but it misidentifies the concrete failure an
implementer would need to reproduce to test the scenario the spec itself
flags as the one this ticket most needs test evidence for.

**Q1 (isReady can lie after a failed fallback), independently checked**: I
confirmed the underlying mechanism is real -
`attemptFallbackInitialization` assigns `self.backend`/`samplingEngine` at
`:214-215` before `warmup()` at `:220`; if `warmup()` throws (via the same
`.batchProcessingFailed` path above), the `catch` at `:226-227` only calls
`publishProgress(.failed(...))`, leaving `self.backend` and `samplingEngine`
both non-nil, so `isReady` (`backend != nil && samplingEngine != nil`,
`:65-67`) would read `true` despite a reported failure. The spec's own Q1
correctly identifies this as real, pre-existing, and appropriately deferred
to `R3` rather than silently absorbed - this is the right call for a
bug-fix spec, not a gap I am asking to be closed here.

**Fix**: replace the `.memoryInsufficient`/`.samplingFailed` examples with
`.batchProcessingFailed` (the actual reachable mechanism), and correct the
`isRecoverable` citation range from `:89-97` to `:89-102` (the property's
actual span).

happens-before to the cache insert). None of the three specs touches
`releaseInstance`, `shutdown()`, or `cleanup()`'s core teardown body - only
*when* `cleanup()`-equivalent logic runs relative to `publishProgress` calls
inside `handleInitializationError`. D1's race condition is therefore neither
fixed nor made more likely by any of these three repairs.

If anything, there is a small, second-order effect in the opposite
direction: today, D8 causes every load failure (recoverable or not) to
deliver **no** `.failed` event, so a caller cannot distinguish failure from
success and has no trigger to call `releaseInstance(forceShutdown: true)`.
Once ODC-0012 and ODC-0015 both land, `Catalyst.generate()`'s existing `if
case .failed(let message) = progress { ... throw }` branch (`:399-403`,
already present, unable to fire today) starts firing correctly on failure,
which routes more failures through `releaseInstance(forceShutdown: true)`.
Per `:504`, `forceShutdown: true` skips the `if !forceShutdown &&
instance.isReady` branch entirely - the exact branch that creates D1's race.
So landing these three tickets very slightly *reduces* exposure to D1 by
routing more calls away from the racy branch, never increases it. This is
worth recording so a future reader does not have to re-derive it, but it
does not change any of the three verdicts or require a spec change.

## Findings, consolidated

1. **[BLOCKING] ODC-0011, `## In-scope repair` step 3**: as worded, the
   repaired `ResponseMetadata` construction keeps `completionReason: .natural`
   hardcoded inside `ResponseMetadata` itself, while only the outer
   `StreamChunk.completion(reason:)` gets the real reason. No test in the
   flip table would catch this. Fix: state explicitly that
   `ResponseMetadata`'s own `completionReason:` argument must be built from
   the real, returned reason; add an assertion comparing
   `metadata?.completionReason` to `metadata?.responseMetadata?.completionReason`
   post-fix.
2. **[BLOCKING] ODC-0012, `## Review record`**: overstates the ordering
   hazard by claiming the non-recoverable path would also hang if ODC-0015
   landed first, alone. Traced against ODC-0015's own design (its explicit
   safety-net `cleanup()` call on that branch), only the recoverable/fallback
   branch (both its success and failure outcomes) would hang. Fix: narrow
   the claim to the branch it actually applies to. The mandatory landing
   order itself is unaffected and remains required.
3. **[BLOCKING] ODC-0015, `## In-scope repair` step 3 and `## Regression risks`**:
   cites `.memoryInsufficient` (never thrown anywhere in `Sources/`) and
   `.samplingFailed` (only thrown during sampler-chain construction or
   token-sampling, never from `warmup()`) as the recoverable errors that
   could surface the leak scenario. The actual, sole reachable mechanism is
   `.batchProcessingFailed`, thrown by `LlamaBridge.processBatch` inside
   `LlamaCppBackend.warmup()`. Fix: replace the cited examples.
4. **[MINOR] Two off-by-one `path:line` citations**: ODC-0015 cites
   `samplingEngine`'s assignment at `LlamaInstance.swift:114`; it is at
   `:113`. ODC-0012's regression-risk section cites
   `Catalyst.swift:398` for the third `isComplete` guard; it is at `:399`.
5. **[MINOR] Test-coverage gap tied to finding 1**: no characterization test,
   present or planned in any of the three specs' flip tables, ever asserts
   on `StreamChunk.metadata?.responseMetadata?.completionReason`. Should be
   added regardless of how finding 1 is resolved, since it is a real blind
   spot in the suite's coverage of `ResponseMetadata`.
6. **[OBSERVATION, non-blocking]** `MLXInstance.swift:310-315` already
   implements the correct `if progress.isComplete` gate ODC-0012 proposes,
   unmentioned by any of the three specs. Worth citing as corroborating,
   already-shipping evidence that the change is safe in this codebase; not
   required for approval.
7. **[OBSERVATION, non-blocking]** Fixing D2/D3/D8 does not worsen D1
   (attack 10 above); if anything it very slightly reduces D1's exposure by
   routing more failures through `releaseInstance(forceShutdown: true)`,
   which bypasses D1's racy caching branch. No spec change required; worth
   recording in whichever of these specs' review records survives to
   `APPROVED` so it is not re-litigated later.
